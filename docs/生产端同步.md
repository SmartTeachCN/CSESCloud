# 生产端同步（CI/CD 与在线更新）

> 本文说明 CSES Cloud V3 的「提交 → CI 构建 → 发布产物 → 生产服务器检查/拉取更新 → 失败回滚」全流程。
> 相关代码：
> - `.github/workflows/ci.yml` —— 每次 push 构建并校验
> - `.github/workflows/release.yml` —— 打 tag 时产出可部署的发布包
> - `scripts/sync-production.mjs` —— 生产服务器上的检查/更新/回滚脚本（纯 Node，零新增依赖）
> - `server/lib/update-sync.js` —— 配置、状态、锁、备份索引、GitHub API 查询（脚本与管理接口共用）
> - `server/lib/build-info.js` —— 读取当前部署的构建信息（`build-info.json` → `.git` → `package.json`）
> - `server/lib/env-load.js` —— 零依赖加载仓库根 `.env`
> - `server/api/system/update.js` —— 管理接口（版本/检查/状态/更新/回滚）
> - `server/api/system/health.js` —— 公开健康检查（更新后探活、监控探活）

---

## 1. 整体流程

```
开发者 push
   │
   ├─ CI（.github/workflows/ci.yml）：Node 22 + pnpm 10 → 语法校验 → 安装依赖 → 构建 dist/
   │      └─ 上传 cses-cloud-v3-dist（Actions artifact，保留 7 天，仅供排查）
   │
   └─ 打 tag（v3.0.0 之类）→ Release（.github/workflows/release.yml）：
          git archive 取 git 跟踪的源码 + 本次构建的 dist/ + build-info.json
          → cses-cloud-v3-<tag 去 v>.tar.gz
          → cses-cloud-v3-<tag 去 v>.zip
          → SHA256SUMS.txt
          → GitHub Release（草稿=false；tag 带 - 后缀视为 prerelease）
                     │
                     ▼
生产服务器：
   pnpm sync:check        # 只读：对比本地 build-info 与上游 Release / 分支最新提交
   pnpm sync:dry-run      # 演练：下载 + 校验 + 解包 + 预演差异，但不改动部署
   pnpm sync:apply        # 正式更新：备份 → 替换 → 依赖 → 重启 → 健康检查（失败自动回滚）
   或使用管理接口 /api/system/update?action=...
```

设计原则：

1. **产物是唯一真源**：生产端只在「git 跟踪的源码 + CI 构建的 dist/」这份产物上更新，不在服务器上构建前端。
2. **运行期数据永不覆盖**：`data/`、`node_modules/`、`.git/`、`.env*`、`exports/`、`logs/` 在替换时整层保留（任意层级同名目录也保留，例如 `frontend/node_modules/`）。
3. **先备份后替换，失败自动回滚**；备份是最新的「代码快照」，回滚会连同依赖与重启一起处理。
4. **零新增依赖**：只使用 `node:` 内置模块；解包用系统 `tar`（Windows 10+ 自带 bsdtar，Linux 自带 GNU tar）。
5. **密钥只放环境变量 / CI secrets**：本机制不引入任何新密钥文件，`UPDATE_SYNC_TOKEN` 只存在于服务器环境变量里。

## 2. CI 产物与 `build-info.json`

Release 资产固定为三个文件（脚本按名字匹配，不要改名）：

| 资产 | 说明 |
|---|---|
| `cses-cloud-v3-<tag 去 v>.tar.gz` | 源码 + `dist/` + `build-info.json`（不含 `node_modules/`、`data/` 运行期数据、`.git/`、`.env*`、`.cred_in.txt`、`debug.flag`）。例：标签 `v3.0.0` → `cses-cloud-v3-3.0.0.tar.gz` |
| `cses-cloud-v3-<tag 去 v>.zip` | 与 tar.gz 内容一致，供 Windows 手工解压排查 |
| `SHA256SUMS.txt` | `sha256sum` 格式，覆盖上面两个文件 |

产物根目录的 `build-info.json` 由 Release 流水线写入，`server/lib/build-info.js` 读取它来展示/比较版本：

```json
{
  "version": "3.0.0",           // 标签去掉 v 前缀（否则回退 package.json 的 version）
  "tag": "v3.0.0",              // 原样标签
  "commit": "<git sha>",        // 该标签的提交
  "branch": "CSES-Cloud-V3",     // tag 触发时取仓库默认分支；手动发布时取所选 ref
  "buildTime": "2026-10-31T06:00:00.000Z",
  "generator": "github-actions"
}
```

读取优先级（`server/lib/build-info.js`）：

1. 部署目录的 `build-info.json`（CI 产物）；
2. 直读部署目录的 `.git/`（`HEAD`、`refs/`、`packed-refs`、`logs/HEAD`，不依赖外部 git 命令；部署时保留 `.git/` 即可用）；
3. 尝试 `git` 命令（Git 可用时兜底）；
4. `package.json` 的 `version`。

结果按文件 mtime 缓存，接口与脚本每次调用都足够便宜；替换部署目录后 mtime 变化会自动刷新。

## 3. 环境变量

全部通过环境变量（或仓库根 `.env`，由 `server/lib/env-load.js` 在启动最早期加载）配置，**不要写进代码或提交入库**。

| 变量 | 默认值 | 说明 |
|---|---|---|
| `UPDATE_SYNC_ENABLED` | 未设置 | `1` / `true` / `yes` / `on` 才启用**管理接口**；未启用时接口一律 403 并提示。命令行脚本不受此开关限制（生产端误删开关也应允许运维用 CLI 抢救）。 |
| `UPDATE_SYNC_TOKEN` | 空 | 管理接口写操作凭据，用 `timingSafeEqual` 比较（先 sha256 摘要，长度不同也常量时间）。**强烈建议设置**。 |
| `UPDATE_REPO` | `SmartTeachCN/CSESCloud` | 上游仓库 `owner/repo`。 |
| `UPDATE_BRANCH` | `CSES-Cloud-V3` | 对比「分支最新提交」用的分支。 |
| `UPDATE_GITHUB_TOKEN` | 空 | 可选。仅用于提高 GitHub API 限流（未配置时 60 次/小时）或访问私有仓库。**不要用高权限 token**，`public_repo` 只读即可。 |
| `UPDATE_INSTALL_DIR` | 脚本/服务所在仓库根 | 生产代码目录（要更新的目录）。 |
| `UPDATE_BACKUP_DIR` | `<install>/data/update/backups` | 备份目录（每份备份一个子目录 + `meta.json`）。 |
| `UPDATE_LOG_DIR` | `<install>/data/update/logs` | 同步任务日志目录（一个任务一个 `.log`）。 |
| `UPDATE_TMP_DIR` | `<install>/data/update/tmp` | 下载与解包临时目录（成功后自动清理，失败保留便于排查）。 |
| `UPDATE_MAX_BACKUPS` | `3` | 保留备份份数（0 = 不清理）。 |
| `UPDATE_RESTART_CMD` / `UPDATE_SERVICE` | 空 | 更新/回滚后重启服务的命令，如 `pm2 restart cses-cloud`、`systemctl restart cses-cloud`、`docker restart cses-cloud`。**未配置则不会自动重启**（新代码下次手工重启才生效）。同时配置时 `UPDATE_RESTART_CMD` 优先。 |
| `UPDATE_HEALTHCHECK_URL` | `http://127.0.0.1:${PORT:-8000}/api/system/health` | 更新后探活地址；返回 2xx 且 JSON 的 `code` 为 0（或缺省）视为健康。 |
| `UPDATE_HEALTHCHECK_TIMEOUT_MS` | `120000` | 健康检查最长等待（重启后服务起来需要时间）。 |
| `UPDATE_HEALTHCHECK_INTERVAL_MS` | `2000` | 健康检查重试间隔。 |
| `UPDATE_INSTALL_CMD` | `pnpm install --frozen-lockfile` | 依赖安装命令（`node_modules/` 缺失或 `pnpm-lock.yaml` 变化时才执行）。 |
| `UPDATE_PRESERVE` | 空 | 追加「不覆盖」的目录/文件名，逗号分隔（默认已含 `data,node_modules,.git,.env,.env.local,.env.production,.env.development,exports,logs`）。 |
| `UPDATE_REQUEST_TIMEOUT_MS` | `15000` | 单次 GitHub API 请求超时。 |
| `UPDATE_API_BASE` | `https://api.github.com` | 仅用于自建代理 / 测试环境（一般不用改）。 |
| `PORT` | `8000` | 服务端口（同时决定默认健康检查地址）。 |

> `.env` 会被 `server/index.js` 第一行 `require('./lib/env-load')` 加载；已存在的真实环境变量优先，`.env` 只补空缺。支持 `#` 注释、`export KEY=VALUE`、单/双引号、行内注释。生产环境推荐直接在 systemd `Environment=` / pm2 `env:` / 容器环境变量里配置，`.env` 记得 `chmod 600`。

## 4. 服务器上的两种部署方式

### 4.1 systemd

```ini
# /etc/systemd/system/cses-cloud.service
[Unit]
Description=CSES Cloud V3
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/cses-cloud
# 非密钥配置
Environment=PORT=8000
Environment=HOST=0.0.0.0
Environment=UPDATE_SYNC_ENABLED=1
Environment=UPDATE_REPO=SmartTeachCN/CSESCloud
Environment=UPDATE_BRANCH=CSES-Cloud-V3
Environment=UPDATE_RESTART_CMD=/usr/bin/systemctl restart cses-cloud
Environment=UPDATE_HEALTHCHECK_URL=http://127.0.0.1:8000/api/system/health
EnvironmentFile=/opt/cses-cloud/.env        # 放密钥：UPDATE_SYNC_TOKEN / UPDATE_GITHUB_TOKEN，chmod 600

ExecStart=/usr/bin/node server/index.js
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

> ⚠️ 用 systemd 的 `ExecReload` + `UPDATE_RESTART_CMD=systemctl reload-or-restart cses-cloud` 更稳；直接 `systemctl restart` 在更新进程本身由 systemd 托管时也没问题（更新进程是独立 CLI 进程）。

### 4.2 pm2

```bash
# 首次：先按常规方式装好依赖并启动
cd /opt/cses-cloud
pnpm install --frozen-lockfile
PORT=8000 pm2 start server/index.js --name cses-cloud
pm2 save

# 在 pm2 环境里加同步配置（写入 ecosystem 文件或 --update-env）
pm2 restart cses-cloud --update-env \
  UPDATE_SYNC_ENABLED=1 \
  UPDATE_RESTART_CMD="pm2 restart cses-cloud --update-env" \
  UPDATE_SYNC_TOKEN="<随机长串>"
```

`ecosystem.config.js`（推荐，避免每次手工传环境变量）：

```js
module.exports = {
  apps: [{
    name: 'cses-cloud',
    script: 'server/index.js',
    cwd: '/opt/cses-cloud',
    env: {
      PORT: 8000,
      UPDATE_SYNC_ENABLED: '1',
      UPDATE_RESTART_CMD: 'pm2 restart cses-cloud --update-env',
      UPDATE_HEALTHCHECK_URL: 'http://127.0.0.1:8000/api/system/health',
      // 密钥建议放 .env（EnvironmentFile 等价物），不要提交到仓库
    },
  }],
};
```

### 4.3 权限与目录

- 「执行更新的用户」必须对 `UPDATE_INSTALL_DIR`、备份目录、日志目录有读写权限；用 systemd 时可以让更新脚本 `sudo -u` 或直接以服务用户执行。
- 备份与日志默认落在 `data/update/`（随 `data/` 一起被保留，不会在更新中被覆盖），请确保磁盘余量 ≥ 2 份代码体积。
- 建议把 `data/update/` 加入 `.gitignore`（运行期数据，不属于代码）。

## 5. 使用方法

### 5.1 命令行（推荐）

```bash
# 0) 先看当前部署与上游差异（只读）
node scripts/sync-production.mjs --check
pnpm sync:check                     # 等价快捷方式

# 1) 演练：下载 + SHA256 校验 + 解包 + 预演差异，不改动部署、不重启
node scripts/sync-production.mjs --apply --dry-run --yes
pnpm sync:dry-run

# 2) 正式更新（会备份、替换、按需安装依赖、重启、健康检查；失败自动回滚）
node scripts/sync-production.mjs --apply --yes
pnpm sync:apply

# 3) 回滚到最近一次备份（或指定某一份）
node scripts/sync-production.mjs --rollback --yes
node scripts/sync-production.mjs --rollback --backup 20261031-060000-2447e47 --yes

# 机器可读输出（便于 CI / 脚本判断；日志走 stderr）
node scripts/sync-production.mjs --check --json --exit-code
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--check` / `--apply` / `--rollback` | 动作（默认 `--check`） |
| `--dry-run` | 演练模式：只读检查 + 下载校验解包 + 预演差异；不备份、不替换、不重启 |
| `--yes` / `-y` | 非交互确认；**无 TTY 时不加会直接报错退出**（不会卡住） |
| `--json` | JSON 输出（日志改走 stderr） |
| `--exit-code` | 配合 `--check`：有新版本退出码 `10`，已是最新 `11` |
| `--tag v3.0.0` | 指定 Release 标签（默认 Latest Release） |
| `--backup <名称>` | 回滚时指定备份目录名 |
| `--no-install` | 跳过依赖安装 |
| `--force-install` | 强制安装依赖 |
| `--skip-verify` | 跳过 SHA256 校验（不推荐） |
| `--allow-missing-dist` | 允许产物缺 `dist/index.html`（仅特殊场景） |
| `--verbose` | 更详细的进度 |

退出码：`0` 成功 / `1` 失败 / `2` 参数或使用错误 / `10` 有更新（`--exit-code`） / `11` 已最新（`--exit-code`）。

### 5.2 管理接口

统一入口：`/api/system/update?action=...`（文件即端点：`server/api/system/update.js`）。
鉴权任选其一：

```bash
# 方式 A：同步凭据（推荐给脚本/监控）
-H "X-Update-Token: $UPDATE_SYNC_TOKEN"
# 或 -H "Authorization: Bearer $UPDATE_SYNC_TOKEN"

# 方式 B：最高管理员登录后的会话 Cookie（浏览器里已登录管理员）
```

| 方法 | action | 作用 |
|---|---|---|
| GET | `version`（默认） | 当前版本/提交/构建时间、运行时长、同步配置概况、最近一次任务状态 |
| GET | `check` | 对比上游 Release / 分支最新提交与本地 `build-info`；可带 `&tag=v3.0.0` |
| GET | `status` | 任务状态：是否运行中、最近一次结果、日志尾部、备份列表 |
| GET | `backups` | 备份列表（名称/时间/来源版本/目标版本） |
| POST | `apply` | 触发后台更新任务，立即返回 `job_id`；可带 body `{"tag":"v3.0.0","no_install":true}` |
| POST | `rollback` | 触发后台回滚，可带 body `{"backup":"<备份目录名>"}` |

示例：

```bash
BASE=https://cloud.example.com
TOKEN=<UPDATE_SYNC_TOKEN>

# 版本信息
curl -s "$BASE/api/system/update?action=version" -H "X-Update-Token: $TOKEN" | jq

# 检查更新
curl -s "$BASE/api/system/update?action=check" -H "X-Update-Token: $TOKEN" | jq '.data | {update_available, recommended_action, release: .release.tag, branch_head: .branch_head.sha}'

# 触发更新（异步），随后轮询 status
curl -s -X POST "$BASE/api/system/update?action=apply" -H "X-Update-Token: $TOKEN" | jq
watch -n 3 "curl -s '$BASE/api/system/update?action=status' -H 'X-Update-Token: $TOKEN' | jq '.data | {running, last: .last.status}'"

# 回滚
curl -s -X POST "$BASE/api/system/update?action=rollback" -H "X-Update-Token: $TOKEN" | jq
```

统一响应风格与其它接口一致：成功 `{"code":0,"message":"ok","data":{...}}`，失败 `{"code":<非0>,"message":"...","data":...}`。
写操作会写审计日志（`Auth.logAudit`，`action=update_apply` / `update_rollback`，含操作者与 job id）。

`GET /api/system/health`（公开，无需鉴权）返回 `{"code":0,"data":{"ok":true,"service":"cses-cloud","version":"...","uptime_seconds":...}}`，供更新后探活、反向代理/监控探活使用。

## 6. 更新任务做了什么（`--apply`）

| 步骤 | 行为 | 失败时 |
|---|---|---|
| 1 | 预检查：部署目录像不像 CSES Cloud、系统有没有 `tar`、并发锁、配置提示 | 中止，无改动 |
| 2 | 查询上游 Release（含产物与 `SHA256SUMS.txt`） | 中止，无改动 |
| 3 | 下载产物与校验清单到 `data/update/tmp/download-<job>` | 中止，无改动 |
| 4 | 校验 SHA256 | 中止，无改动 |
| 5 | 解包到 `data/update/tmp/staging-<job>`，校验 `package.json` / `server/index.js` / `schema.sql` / `dist/index.html`，读取产物里的 `build-info.json` | 中止，无改动 |
| 6 | 备份当前代码 → `data/update/backups/<YYYYMMDD-HHmmss>-<commit>/`（含 `meta.json`）。备份**不含** `data/`、`node_modules/`、`.git/`、`.env*`、`exports/`、`logs/` | 中止，无改动 |
| 7 | 镜像替换代码：产物有则覆盖、产物没有则删除；保留名单（任意层级）不覆盖也不删除；lockfile 变化会被记录 | **自动回滚** |
| 8 | 依赖安装：`node_modules/` 缺失或 `pnpm-lock.yaml` 变化时执行 `UPDATE_INSTALL_CMD` | **自动回滚** |
| 9 | 重启服务（`UPDATE_RESTART_CMD`）→ 轮询健康检查（`UPDATE_HEALTHCHECK_URL`） | **自动回滚**（回滚后同样重启 + 健康检查） |
| 10 | 收尾：清理临时目录、按 `UPDATE_MAX_BACKUPS` 清理旧备份、写 `state.json` 与任务日志 | — |

要点：

- **保留名单**默认：`data`、`node_modules`、`.git`、`.env`、`.env.local`、`.env.production`、`.env.development`、`exports`、`logs`；可用 `UPDATE_PRESERVE` 追加。命中规则是「路径里任意一段等于这些名字」，所以 `frontend/node_modules/` 也不会被删。
- **备份是回滚源**：`data/update/backups/<stamp>-<commit>/meta.json` 记录 `from`（更新前版本/提交）与 `to`（目标 Release），`action=rollback` 默认选最新一份。
- **并发保护**：`data/update/sync.lock`（含 pid/主机/开始时间）。崩溃残留的锁会按「进程已死」自动清理；6 小时以上的锁视为僵尸。
- **状态与日志**：`data/update/state.json`（`running` / `last` / 最近 20 次历史）、`data/update/logs/<job>.log`（完整任务输出）。
- **未配置 `UPDATE_RESTART_CMD` 时**：替换会完成，但不会重启、不做健康检查（脚本会明确警告；新代码在下次手工重启后生效）。建议一定配置。

## 7. 回滚

```bash
pnpm sync:rollback                 # 回滚到最近一次备份
node scripts/sync-production.mjs --rollback --backup 20261031-060000-4f8cf20 --yes
# 或
curl -s -X POST "https://cloud.example.com/api/system/update?action=rollback" -H "X-Update-Token: $TOKEN"
```

回滚做的事：从备份镜像恢复代码（同样保留 `data/` 等运行期目录）→ `node_modules/` 缺失时安装 → 重启 → 健康检查。

备份目录（手工保底方案）：

```bash
ls -1 data/update/backups/
# 20261031-060000-4f8cf20/         ← 更新前的代码快照 + meta.json
# 20261030-120000-2447e47/
```

极端情况下（脚本本身坏掉），可以手工把备份目录的内容拷回部署目录（**不要**删除 `data/`、`node_modules/`、`.env`），再重启服务。

## 8. 故障排查

| 现象 | 原因 / 处理 |
|---|---|
| 接口返回 403「生产端同步未启用」 | 没设置 `UPDATE_SYNC_ENABLED=1`，或设置后没重启服务。检查 `action=version` 里的 `sync.enabled`。 |
| 接口返回 401「未登录 / 同步凭据无效」 | 请求头没带 `X-Update-Token`（或值与 `UPDATE_SYNC_TOKEN` 不一致），且当前也没有最高管理员会话。 |
| 接口返回 403「权限不足」 | 用的是普通登录账号；需要最高管理员，或改用同步凭据。 |
| `check` 返回 502 / 脚本「检查失败」 | GitHub API 不可达（服务器无外网 / 需要代理）、被限流（未配 `UPDATE_GITHUB_TOKEN`），或 `UPDATE_REPO` / `UPDATE_BRANCH` 写错。先用 `curl -I https://api.github.com` 确认连通。 |
| 「上游暂无 Release」 | 上游还没打 tag；CI 的 `ci.yml` 只构建不发布，Release 由 `release.yml` 在 push `v*` 标签时产生。 |
| 「Release 中没有 .tar.gz 产物」 | Release 资产命名不符合约定（必须是 `cses-cloud-v3-<tag>.tar.gz` 等），或 Release 是手工建的。 |
| 「产物校验失败」 | 下载不完整或资产被替换；重试一次，或核对 `SHA256SUMS.txt`。 |
| 「没有可用的备份」 | 从没成功执行过 `--apply`（备份在更新前创建）；`--rollback` 无从恢复。 |
| 「已有同步任务正在运行」 | 有锁未释放。等任务结束；确认进程已死后可删除 `data/update/sync.lock`，或按 `action=status` 里的 holder 信息处理。 |
| 「系统缺少 tar 命令」 | Linux 安装 `tar`；Windows 10+ 自带 `bsdtar`（`C:\Windows\System32\tar.exe`）。 |
| 健康检查一直失败 | 服务没起来（看 `data/update/logs/*.log` 与 `pm2 logs` / `journalctl -u cses-cloud`）、端口不对、`UPDATE_HEALTHCHECK_URL` 写错、或反向代理只允许外部域名。脚本在健康检查失败时会自动回滚，回滚后仍失败会提示手工处理。 |
| Windows 下替换报 EBUSY/EPERM | 有进程占用了要替换的文件（编辑器/杀软/服务）。先停服务再更新，或把部署目录排除出实时防护扫描。 |
| 依赖装不上 | 服务器缺 pnpm / 无外网。可预先在服务器配好 pnpm 与 registry 镜像，或 `--no-install` 手工安装；产物不含 `node_modules` 是刻意的（体积与原生模块兼容性）。 |
| 更新后仍显示旧版本 | 浏览器缓存（刷新/强刷）；或 `build-info.json` 没被替换（检查 `data/update/state.json` 的 `last` 与 `[7/9]` 步骤日志）。 |

日志位置：

```bash
tail -f data/update/logs/$(ls -t data/update/logs | head -1)
cat data/update/state.json | jq
```

## 9. 安全说明

- **密钥只放环境变量 / CI secrets，不入库**：`UPDATE_SYNC_TOKEN`、`UPDATE_GITHUB_TOKEN` 不写进代码、不写进提交、不打进发布产物；`.env` 请在服务器上创建并 `chmod 600`，同时确认它被 `.gitignore` 忽略。
- **发布包不夹带敏感文件**：`release.yml` 会用 `git archive` 只取被 git 跟踪的文件，并对 `.env*`、`.cred_in.txt` 等做「出现即失败」的兜底检查；`data/` 下的运行期数据也会被剔除。
- **管理接口默认关闭**：`UPDATE_SYNC_ENABLED` 不开就是 403；开启后仍必须令牌或最高管理员。
- **令牌比较是常量时间**：先把两边 sha256 摘要再 `timingSafeEqual`，长度不同也不泄漏。
- **README 徽章与 Actions 日志**里不要放 token；GitHub 会自动遮蔽 secrets。
- **GitHub token 最小权限**：只需要读仓库/Release（公共仓库甚至可以不配）。
- **审计**：更新/回滚都会写 `audit_logs`（`update_apply` / `update_rollback`），含操作者标识与 job id，可在「操作记录」页查看。

生成一个同步凭据：

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

## 10. 已知限制

1. **自动更新只认 Release 产物**：分支有新提交但没打 tag 时，`check` 会提示 `branch-ahead`，`--apply` 无法更新（只能等发版，或人工 `git pull` + `pnpm build`）。
2. **替换是逐条目镜像，不是整个目录的原子 rename**：极端断电/强杀可能留下「一半新一半旧」的目录。此时用 `--rollback` 或备份目录恢复即可（备份在替换前完成）。
3. **备份不含 `node_modules/`**：节省空间，回滚时若依赖已变化会自动重装或需要 `--force-install`。
4. **健康检查默认打本机**：如果服务只监听公网/反代域名，请把 `UPDATE_HEALTHCHECK_URL` 改成实际可达地址（或用 `https://cloud.example.com/api/system/health`）。
5. **Windows 生产环境**：脚本能跑（bsdtar 解包），但文件占用比 Linux 更容易触发 EBUSY；推荐 Linux 部署 + Windows 只做开发/演练。
6. **`.env` 只在进程启动时读一次**：改 `.env` 后需要重启服务生效。
